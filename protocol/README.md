# Use-conditioned GeoAI due-diligence decision record

This directory makes the manuscript's protocol operational rather than leaving it as a
narrative checklist.

- `protocol_decision_record.schema.json` is the normative JSON Schema for a completed audit.
- `ftw_turkiye_decision_record.json` is the schema-validated record generated for this case.
- `../tables/table_0_protocol_decision_record.csv` is the flattened, human-readable record
  generated by the analysis notebook for the FTW Türkiye demonstration.

The protocol separates two questions that must not be collapsed:

1. **Audit completeness:** was the required evidence obtained and was the test executed?
2. **Fitness for a declared use:** does the evidence meet the use-specific acceptance
   requirement?

An audit stage therefore has one of three evidence outcomes: `pass`, `fail`, or
`indeterminate`. An `indeterminate` result is not silently treated as a pass. The final action
is one of:

- `adopt`: evidence meets every mandatory requirement for the declared use;
- `adopt_with_restrictions`: use is allowed only within recorded thematic, spatial,
  temporal, or attribute restrictions;
- `external_validation_required`: the product cannot support the use until independent
  reference evidence is supplied;
- `reject_for_declared_use`: one or more non-negotiable requirements fail.

The schema does not encode universal numerical quality thresholds. Thresholds belong to the
declared use, risk level, and decision consequences in Stage 0. This is the central distinction
between a generic product-quality checklist and a fitness-for-use decision protocol.

An `adopt_with_restrictions` record must include at least one explicit, machine-readable
restriction. An unrestricted `adopt` record must have neither restrictions nor unresolved
evidence gaps. Stage-level outcome/action pairs are constrained by the schema, and the notebook
applies additional semantic decision rules across all stages and the final action (for example,
any `stop` action requires `reject_for_declared_use`).

## Minimal validation

Any JSON decision record can be structurally validated with a Draft 2020-12 JSON Schema
validator. Cross-stage/final-action consistency is additionally checked by the notebook's
semantic decision-rule validator. The CSV generated for the manuscript is deliberately
flattened for inspection and publication; the field names correspond directly to the schema
properties.

## Versioning

The protocol version is independent of the audited product version. A completed record must
pin both, together with the code revision and evidence artefact identifiers. Changing a use
requirement, product input, analytical rule, or evidence artefact requires a new decision-record
identifier.
